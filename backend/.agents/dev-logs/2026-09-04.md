## 🔍 Step 0 ~ Step 2 分析與選型結論
1. **任務分類 (Step 0)**:
   - 屬 **Track B (既有需求變更與模型/API 擴充)**。
2. **通訊協定評估 (Step 2 - communication-evaluator)**:
   - 預算管理為典型之同步 Request-Response CRUD 操作（查詢清單、查詢單一、新增、修改、刪除）。
   - 無雙向協同編輯或多方即時聊天需求（不需 Socket.IO）。
   - 無長時間進度推播或 Server-to-Client 串流需求（不需 SSE）。
   - **選型決策**：採用標準 **HTTP REST API**。
3. **資料庫相容性與精度分析**:
   - 原 schema 中 `amount` 為 `Float`，為保持領域模型一致性與避免 JSON 序列化產生 `Decimal` 轉字串問題，Prisma 模型使用 `usedAmount Float @default(0) @map("used_amount")`。
   - 規格書中同步提供標準 PostgreSQL (`NUMERIC(12, 2)`) 與 MySQL (`DECIMAL(12, 2)`) 建表 DDL 與 CHECK 非負約束。
4. **業務邊界防護**:
   - 限制 `usedAmount >= 0`、`amount >= 0`。
   - 容許超支情境（`usedAmount > amount` 不阻擋儲存）。
   - 日期有效性檢驗（`startDate <= endDate`，違規拋出 400 Bad Request）。
   - 預設值回填（未傳入 `usedAmount` 自動補 `0`）。
