## 🔍 Step 0 ~ Step 2 分析結論
1. **任務分類 (Step 0)**:
   - 屬 Track B (通訊層架構升級與加密模組化擴充)。
2. **傳輸協定評估 (communication-evaluator)**:
   - 針對 HTTP REST API 請求/回應酬載之對稱加密 (AES-CBC Pkcs7 與動態時間戳 Key/IV 衍生)。
3. **架構設計要點 (Needs Analysis)**:
   - **Strategy 介面抽象**: 定義 `IPayloadCryptoStrategy` 與 `PAYLOAD_CRYPTO_STRATEGY_TOKEN`，支援隨時抽換或更換加密演算法 (AES-CBC, AES-GCM, Mock)。
   - **互通性保證**: Key = `SHA256(${secretKey}:key:${ts})`，IV = `SHA256(${secretKey}:iv:${ts})[0..16]`，與前端 `crypto-js` 100% 互通。
   - **透明請求解密**: 採用 NestJS `PayloadDecryptMiddleware`，於 `ValidationPipe` 執行前將 `req.body` 還原，避免驗證失敗。
   - **開發/生產環境自適應**:
     - 開發模式 (`VITE_ENABLE_ENCRYPTION="false"` / 明碼)：支援明文傳輸，亦智能相容加密請求。
     - 生產模式 (`VITE_ENABLE_ENCRYPTION="true"` 或 `NODE_ENV=production`)：強制加密，未加密請求拒絕。
   - **透明回應加密**: 於 `TransformInterceptor` 中自動將 `res_body` 包裝為 `{ encryptedData: cipherText }` 並帶入時間戳 Header。
